# Plan: Windows-only prototype build action for Handy

## Objective

Add one GitHub Actions workflow that builds Handy for 64-bit Windows only, on
demand, for personal prototyping. It should produce downloadable Windows
installer artifacts without requiring release signing or changing the existing
cross-platform workflows.

## Findings from the current project

- [`.github/workflows/build.yml`](../.github/workflows/build.yml) is already a
  reusable workflow (`workflow_call`) and contains the Windows-specific build
  path: Windows runner preparation, Rust and Bun setup, Vulkan SDK installation,
  VC++ runtime staging, Tauri packaging, Windows package auditing, and artifact
  upload.
- [`main-build.yml`](../.github/workflows/main-build.yml),
  [`build-test.yml`](../.github/workflows/build-test.yml), and
  [`pr-test-build.yml`](../.github/workflows/pr-test-build.yml) already call
  the reusable workflow, but each includes multiple macOS, Linux, Windows x64,
  and Windows ARM64 matrix entries.
- [`release.yml`](../.github/workflows/release.yml) is also unsuitable as the
  prototype entry point because it is release-oriented and includes signing and
  release asset behaviour.
- [`BUILD.md`](../BUILD.md) confirms that Windows produces MSI and NSIS bundles,
  and notes that local signing is not required for development. The CI workflow
  already supplies the Windows-only runtime checks that are useful for this
  prototype build.
- The repository currently has only `.vscode/extensions.json`; there is no
  existing VS Code task configuration to trigger a workflow.

## Proposed workflow

Create a new file such as
`.github/workflows/windows-prototype-build.yml` with the following shape:

1. Give it a clear name such as `Windows Prototype Build`.
2. Use `workflow_dispatch` as the only trigger. Add a `ref` input so a branch,
   tag, or commit can be selected from VS Code or the Actions UI. Default it to
   the current branch/ref where GitHub Actions supports that expression; if the
   expression is awkward for manual dispatch, default to `main` and document
   passing the current branch explicitly.
3. Add an optional boolean `debug` input only if a debug package is useful for
   the development cycle. Otherwise keep the first version as a release-mode
   build, since that matches the existing packaging and audit path.
4. Define a single job using the existing reusable workflow:

   - `platform: windows-latest`
   - `target: x86_64-pc-windows-msvc`
   - `build-args: ""`
   - `upload-artifacts: true`
   - `asset-prefix: handy-prototype`
   - `sign-binaries: false`
   - `ref: ${{ inputs.ref }}`
   - `is-debug-build: ${{ inputs.debug }}` if the debug input is retained
   - `secrets: inherit` only if required by the reusable workflow; with signing
     disabled, verify whether it can be omitted safely.

5. Keep the workflow x64-only initially. Windows ARM64 can be added later as a
   separate deliberate choice because it uses a different runner and compiler
   configuration in `build.yml`.
6. Do not duplicate the build steps from `build.yml`, and do not modify the
   existing workflows. This keeps fixes to the shared Windows build path
   automatically available to the prototype workflow.
7. Confirm the resulting artifact name is predictable, for example
   `handy-prototype-x86_64-pc-windows-msvc`, and that it contains the MSI and
   NSIS installer generated by the reusable workflow. The artifact should be
   retained for a short, useful period such as 7 or 14 days if retention is
   made configurable; otherwise retain the existing 30-day default.

## VS Code local trigger

Add a workspace task in `.vscode/tasks.json` that invokes the GitHub CLI rather
than trying to execute the GitHub-hosted Windows runner locally:

```json
{
  "version": "2.0.0",
  "tasks": [
    {
      "label": "Handy: trigger Windows prototype build",
      "type": "shell",
      "command": "gh workflow run windows-prototype-build.yml --ref ${input:handyBuildRef}",
      "problemMatcher": []
    },
    {
      "label": "Handy: watch Windows prototype build",
      "type": "shell",
      "command": "gh run watch --exit-status",
      "problemMatcher": []
    }
  ],
  "inputs": [
    {
      "id": "handyBuildRef",
      "type": "promptString",
      "description": "Branch, tag, or commit to build",
      "default": "main"
    }
  ]
}
```

Implementation details for the task:

- Verify that GitHub CLI is installed and authenticated with
  `gh auth status` before relying on the task.
- Prefer `gh workflow run ... --ref ... --field ...` for dispatch inputs so the
  same task can pass `debug=false` or other future options explicitly.
- `gh run watch --exit-status` should be run against the newly created run ID
  if the trigger task is later changed to capture and pass that ID; otherwise
  the task should first list the latest run for the workflow and watch that run
  to avoid attaching to an unrelated build.
- Add a second task, or a compound task, to open the completed run and its
  artifacts with `gh run view --web` after a successful build. This gives a
  simple VS Code loop: run task, wait for completion, open/download artifact.
- Document that this triggers a remote GitHub-hosted build from VS Code; it is
  not an offline local Windows build. For a true local build, use the commands
  in `BUILD.md` and the local Windows prerequisites described there.

## Authentication and permissions

- Use a GitHub account with permission to dispatch workflows in the repository.
- Run `gh auth login` once, then confirm `gh auth status` from the same shell
  environment VS Code uses.
- The workflow should request only the permissions required by the reusable
  build. Since this is not a release workflow, avoid release creation and
  signing secrets.
- Do not add a push trigger; the purpose is an explicit, personal prototype
  build on demand.

## Validation checklist

1. Validate the workflow YAML and GitHub Actions expression syntax.
2. Dispatch it manually from the Actions UI using a known branch.
3. Confirm the run has exactly one job on `windows-latest`.
4. Confirm the build reaches both MSI and NSIS package creation and passes the
   existing Windows runtime-content audit.
5. Download the artifact and smoke-test installation and launch on Windows.
6. Test the VS Code task with the same branch and verify that it points to the
   expected run and artifact.
7. Verify that existing workflows remain unchanged and still retain their
   current cross-platform behaviour.
8. Update [`.github/workflows/README.md`](../.github/workflows/README.md) only
   if workflow documentation exists there; otherwise add a short section to
   [`BUILD.md`](../BUILD.md) describing the new prototype workflow and VS Code
   trigger.

## Risks and decisions to confirm during implementation

- `sign-binaries: false` is the intended choice for personal prototypes; the
  resulting installers may show normal Windows trust warnings.
- A GitHub-hosted build consumes Actions minutes and needs network access to
  download dependencies and the Vulkan SDK.
- The reusable workflow currently grants `contents: write`; inspect whether
  that permission is required for this non-release invocation and reduce it if
  the called workflow can support a read-only prototype build.
- If the workflow's `ref` input is not accepted as expected by the reusable
  call, use the dispatch event's ref directly and keep the input only for the
  caller's branch selection.
